## 根因与修复

1. **匹配422**：修复前真实 FLASH 输出12项，其中4段 JD 引文被重复用于拆分后的技能项，包括「掌握 Java 与 Spring Boot」「理解 MySQL 索引和事务」「了解 Redis、Git」。旧 validate 因重复引文拒绝整份报告。原始输出仅写到仓库外临时文件，完成后删除；PRO基线未出现重复引文。v2 提示词补充组合要求去重和叶子 JSON Pointer 示例；校验允许空白/全角 ASCII 的格式差异，但保存引文必须还原为原文连续子串。丢弃重复或无效项，至少1项才成功，最多12项；过滤摘要说明分母，分数仅算保留项。全无效时最多一次带校验反馈的重试，仍失败不存报告。
2. **第二次匹配502**：demo 详情缓存超过10分钟后走实时 MCP；AUTO 详情没有已存副本回退。现在 demo、LOCAL_SNAPSHOT 永不要求实时详情；AUTO 的 TOOL_FAILED/无效详情回退为 STORED_SNAPSHOT，保留原缓存与时间，LIVE仍报错。REST匹配、聊天匹配与刷新共用 JobService.detail；GET原本就是读缓存。前端刷新保留返回副本和来源提示，不再立即GET丢掉回退标记。
3. **叙述缺少卡片明细**：教练摘要未包含技能等级与四周内容。现在独立转义的数据消息提供最多5项技能、4周主题/任务、面试STAR/维度/建议及职业前5项理由；模型应概括已展示卡片。额外发现 demo 初始 target「后端开发」不能精确关联职业库，已改种子为规范名称「后端开发工程师」；不覆盖运行中账号的既有目标，已有体验数据需按原重置/目标选择流程更新。
4. **RIS医疗职业靠前**：只看位置加权 Holland，RIS精确匹配的医疗职业压过软件职业，目标/Java技能未进入规则排序。现在全部正分候选先按 Holland 45% + 显式软件方向相关度55% 排序再截断；仅「技术研发」为弱信号，本轮文字/目标/技能的明确软件信号为强信号。无方向时保持原Holland顺序，同分名称/ID稳定。显示相似度仍是原Holland值，理由说明方向信号，不推断专业、不伪造向量命中或引用。
5. **看板澄清偶发**：前端传 jobId，但没有 boardAction，动作由模型推断。AUTO/JOB 的明确整句「把这个岗位加入求职看板」或 boardAction=createApplication 现在确定性生成 WRITE，缺jobId才澄清，仍等待HITL。另在PRO聊天匹配实测中发现动作模型不知道调用方已选择资源；提示词现接收选择状态布尔值，实际ID只由服务端绑定。
