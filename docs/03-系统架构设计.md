## AG-02 首响应关键路径（2026-10-20，待 live 实测）

agent 的 KnowledgeNoteContext 以单次订阅持有的只读预取，让私有笔记召回与 AUTO 规划及独立专家读取重叠。通过既有 career 的 KnowledgeNotesForChat 应用接口读取，owner/查询完全相同时本轮复用；显式 JOB/CAREER 不预取。预取不执行专家工具、不输出事件，不写业务数据；规划、审批和工具仍遵循完整校验与输入 gate。证据、卡片和最终叙述仍等待原检索结果，取消释放预取订阅。没有答案缓存、新模块或进程。

platform 的 DeepSeekRequestSupport 让分类器、各档位及同步/流式适配器共享同一 JDK HttpClient，复用按目标地址管理的连接池；不发启动探测或额外模型请求。ChatService 把每个 delta 对下游的交付移到该块 checkpoint 之前，写入保持串行、节流和终态 CAS，完成事件等待写入；RunRelay 仍先持久化事件再交付 SSE，重连顺序保证保留。每阶段计时与 HTTP 实测口径见延迟脚本 README 和 [10](10-测试与评估方案.md)。
## CP-05 报告驱动的计划更新建议（2026-10-21）

career 的 InterviewPlanUpdates 复用 InterviewLearningSource（bootstrap InterviewLearningBridge → interview 应用服务），只读所属已完成报告的真实 recommendedLearning，不调用生成模型。目标快照保存在既有 interview_learning_plans：任一来源明确选择岗位时必须 jobId 相同；双方都没有 jobId 才允许修剪首尾空白、忽略大小写后角色名完全相同，不做语义近似匹配。仅更新已持久化的报告学习计划，不把聊天卡片或职业目标联动草案当作已保存学习计划。

报告页 GET 按需计算建议，不写计划/审批/完成记录；用户显式确认的 POST 才合并任务。同 owner 先锁用户（NO KEY UPDATE），再锁来源会话和计划，防并发丢失；fingerprint 同时绑定当前报告短板、计划快照、目标、已采纳记录及具体新增任务。确认时重新读取并校验，变化返回409；已成功的同一确认可幂等重放。V50 保存目标快照与采纳摘要，不保存模型答案缓存；旧任务、里程碑、完成状态保留，新增任务 done=false。安全网关与 Agent 审批不变，没有新增可绕过审批的 Agent 写工具。数据库和双视口验证待实测。

## 记忆与测评纵向补齐（2026-10-20，V49）

## 通知与职业后续联动（AG-11 / BD-04 / CD-05 / CD-09，2026-10-20）

identity 的 Notifications 管理用户站内收件箱、已读与未读计数，实现 platform 的小型 NotificationSink 端口；业务模块只传可信 owner、来源唯一键、文案与站内路径，不访问通知表。job 的 DeadlineReminders 读取本模块 applications/jobs，按上海日期扫描 DDL 与面试下一步行动；NewJobNotifications 经 identity 的 UserDirectory 分页枚举活跃非 demo 用户，调用本模块 daily 推荐并对已存真实岗位送达。interview 创建练习时在原事务内发送计划通知。未新增模块、进程、消息中间件或外部日历。

career_target_plans 属于 career：V47 的 career_profiles 触发器在目标/城市改变的同一事务内记录新 revision，覆盖 REST、聊天批准写入和已有记忆导入；升级不回放已有目标，显式再次采纳旧目标时补建缺失联动，清空目标废弃在途工作。CareerTargetPlans 原子认领后在事务外调用 TargetJobSearch、SkillGapService 和 CoachPlanForChat，结果以 revision 条件保存；bootstrap TargetJobSearchBridge 通过 JobService 搜索并携带 owner 配额上下文。搜索和建议部分失败可显式重试，10分钟租约恢复中断工作；迟到的旧目标结果不写入、不通知。页面确认仅记录采用建议，不伪造投递或任务完成。聊天写入仍先审批；CareerWriteTools 在批准保存目标后立即尝试执行同一联动，Orchestrator沿既有多卡事件输出真实生成的skill_gap/roadmap并征求后续确认；后台任务恢复中断工作，CAS防止两条路径重复执行。后续查询属于同一批准步骤，不新增三个人工子步骤。

ProfileSuggestions 定时分批读取真实材料，页面读取也会对账；ProfileEvidenceSource 由 bootstrap ProfileEvidenceBridge 组合 resume/github/interview 的应用接口，跨域不读仓储/表。简历只抽取技能与项目技术，GitHub只用有效快照的非fork且有本人提交仓库，面试只读取最近已完成且有评分报告的优点/待练习事实，不推断技能熟练度。建议、指纹和通知同事务幂等保存；确认时持用户锁重新核对当前来源，合并用户勾选的候选技能，保留最新手工字段，并把已确认事实暴露为 profile.evidence。忽略、来源变更、重复确认与身份隔离均有明确行为。定时对账不抓取GitHub、不调用模型；目标岗位搜索沿用现有可用源，历史快照保留标记。

## Agent 对话卡片、回放与用量（2026-10-20）

编排仍归 agent；显式模式先确定唯一专家，再解析该专家动作，不调用 AUTO 规划模型。JOB 的显式匹配动作仍校验选择资源及模式冲突。Orchestrator 的 ToolCardProjections 只把真实工具返回的 skills 投影为 skill_radar、岗位明确截止日期投影为 campus_calendar、面试报告最后一题投影为 interview_turn_score；原报告与来源保留，没有补造日期、能力或分数。CardCitations 从真实推荐/知识笔记摘录分配本轮数字编号，并作为转义数据交给最终叙述；缺失检索分数保持 null。

platform 的 UsageJournal 在 ModelGateway 的供应商调用边界记录本次调用模型、累计 metadata token、耗时和配置价格估算；ChatService 以认证 owner/run/message 建立 Reactor 关联。阻塞专家调用使用受限 ThreadLocal 桥接且 finally 恢复；岗位匹配把关联显式传入其内部 Reactor 链，修复调用同样归本轮。不会按 owner 全局猜测归属。普通非聊天业务暂无 run/message 关联，仍沿用原额度统计，不冒充聊天日志。聚合从 llm_usage_logs 读取，含规划、安全分类、预取及已发生的取消调用；无 token metadata 的调用保留 usage_reported=false，不猜测 token/费用。

RunRelay 使用既有 WorkbenchEvents 按原 seq 保存新运行全部事件（包括正文、卡片、引用），保留 owner 门禁与幂等键。已有 /workbench 有限历史 API 支持进程重启后的逐事件 UI 回放；/events 优先本机缓冲，缺失时按V49共享事件存储续传。前端回放实例与实时实例隔离，使用同一 agentRun.apply reducer 和卡片组件；回放禁用审批及业务写操作。旧运行没有保存的正文/卡片事件不回填，UI 明示只可回放已记录过程。

## RS-08 / CP-02（2026-10-20）

resume 的 github 包负责用户名、凭据、快照与项目采纳；platform 的 GitHubClient / RestGitHubClient 提供可注入只读 HTTP 适配器，固定 api.github.com、禁止重定向，不使用用户 URL 或 MCP 共享服务凭据。GitHubTokenCipher 复用现有加密配置，以 AES-256-GCM、随机 IV、owner AAD 保存用户 PAT；响应只含 tokenConfigured，无凭据读取接口。网络/FLASH 不持数据库事务，revision 条件写防止设置变更后的迟到覆盖。

career 的 SkillGapService 通过 resume 应用服务读取所属简历版本和 GitHub 快照，通过本模块读取画像/职业技能；SkillGapJobSource 由 bootstrap SkillGapJobBridge 调用 JobService.get 读取已存可见岗位。沿用 career→resume 依赖，无业务仓储跨域访问、无新进程/embedding。新增 GET 分析是确定性只读入口；旧聊天教练的数值技能卡保持既有语义，本切片三档报告在成长页独立展示。

项目采纳由用户明确确认，经 resume 当前版本校验保存 MANUAL_EDIT 新版本；不自动把仓库语言填入个人技术栈，不推断个人角色/贡献。V46 快照及凭据按 owner 隔离、账号删除级联、demo reset 清理。

## MCP 管理与检索调试（2026-10-20）

platform 的 StreamableMcpClient 承担有界 initialize/initialized、tools/list 分页与 tools/call，jobs、搜索和 GitHub 共用；bootstrap 的 McpConnections 组合 CurrentUser、JdbcTemplate 与部署配置，V44 持久化各用户的启停、发现状态和工具 schema。platform 的 McpAccessPolicy 小接口由 bootstrap 实现，岗位客户端按已验证 owner 检查停用状态，不产生反向模块依赖。公开 MCP Server 无 owner，继续使用独立 API-key 门禁。

career 的 RetrievalDebug 只读公开 occupations，经 identity 的 PasswordLoginService.requireStaffId 核验实时 STAFF 角色；不允许指定其他用户笔记。复用中文分词、OccupationEmbeddings、embedding_index_state 和 RRF，向量仅接受本地 bge-m3 的同空间索引。查询词覆盖率重排独立于业务职业推荐，结果明确算法及分数含义，不声称使用交叉编码重排模型。

## 1. 架构原则

认证 IP 限流（S-1，2026-10-09）：platform 的 `AuthRateLimitFilter` 在 Spring Security 的 CORS 之后、控制器及请求正文解析之前，仅限制 POST guest/login/register/staff-login；identity 控制器不重复计数。`AuthRateLimiter` 按客户端 IP 和独立路由桶维护从首次请求起的 60 秒固定窗口，Redis Lua 原子检查、计数和过期保证跨实例一致。无 StringRedisTemplate 时使用 ConcurrentHashMap 原子更新，按分钟在请求时清理过期记录，仅适合测试或单实例；已配置 Redis 故障返回 503/50003，不切换到新的本地计数。本增量不实现 LLM 用量配额。

认证修复（2026-10-08）：identity 的 CurrentUser 同时校验 30 天访客令牌与 12 小时密码登录 JWT；密码使用 BCrypt(12)，签名密钥必须由环境提供至少 64 字节随机值。前端认证 API/DTO 与 QueryClient 位于 shared，统一 store 管理用户与客服登录；身份切换取消查询并清除服务端缓存，迟到响应不会覆盖新身份。已保存访客可继续恢复；JWT 失效后进入重新登录状态，不自动切换访客或重放请求。V12 停用 V11 的未改密公开测试账号并保留数据。刷新 Cookie、访客转账号迁移仍为后续设计。

定向改写生成后端（2026-10-02）：`ResumeOptimizationController → ResumeOptimizationService → ResumeOptimizer → ModelGateway`，使用现有文字模型档位，不新增供应商。resume 模块接收显式 JD 文本，不反向依赖 job 模块。短事务登记幂等请求和每用户单任务，模型阶段在事务外；成功结果与建议批次在一个事务内提交，不修改简历版本。用户后续通过既有 apply-patches 明确采纳。V12 保存私有任务、JD快照及结果，支持历史读取/取消和过期拒绝迟到结果；前端接入在下一提交完成，聊天生成与写工具尚未接入。

简历上传解析已落地（2026-09-19）：`ResumeController → ResumeService → PostgreSQL / ResumeObjectStore(MinIO)` 保存原文件与 QUEUED 任务；数据库轮询 worker 原子领取任务，`ResumeDocumentReader → ResumeExtractor → ModelGateway` 在事务外解析，最后原子保存结构化版本与 READY 状态。PDFBox 提取 PDF 文本并渲染每页以保留混合内容；DOCX 通过有大小限制的 ZIP + 禁用外部实体的 XML 读取正文、页眉、页脚及嵌入 PNG/JPEG，图片走视觉模型。dev 图文路由默认共用 DeepSeek Key；图像使用同供应商 OpenAI 兼容适配器。当前不依赖 Tika 自动解析器。用户隔离复用 CurrentUser；文件和简历业务归属 resume 模块。10 分钟任务租约失效后转 FAILED，用户可重试；token 阻止过期 worker 覆盖新任务。所有实例可安全领取，单实例每次处理一个任务。ResumeModelSettings 在 resume 应用层保存访客偏好，通过平台 ModelGateway 的无密钥目录选择已配置档位；上传与重试复制档位到任务中，解析器使用任务选择。

当前实现（2026-09-18）：`AgentController → ChatService → ConversationService / ModelGateway → PostgreSQL / DeepSeek`。identity 模块通过 application 层的 `CurrentUser` 提供访客身份校验，agent 模块只接收可信 owner ID。会话领域使用 JdbcTemplate 和短事务管理会话、消息与运行，数据库锁不跨模型调用；Controller 处理 SSE、心跳及订阅释放。默认 dev 环境仍启动 PostgreSQL/Flyway/JPA/Redis，尚未接入的 Embedding/VectorStore 在 dev 关闭。该段记录早期文字链路；M1 占位编排见上文，真实业务专家仍为后续设计。启动操作见 [backend/README](../backend/README.md)。

1. **前端是产品，后端是 AI 能力接入层**：契合赛方定位。后端职责收敛为认证、Agent 编排、模型与工具接入、数据持久化；所有用户可感知的智能体过程都以事件形式推送到前端渲染。
2. **一切可流式、可中断、可回放**：Agent 运行以事件流（SSE）为一等公民，事件同时落库。
3. **安全内建于工具循环**：读写分级、审批、参数校验、输出审核作为 Advisor 嵌入 Spring AI 的调用链。
4. **数据最小化与端侧优先**：隐私敏感的实时感知（语音识别、表情姿态）在浏览器完成，只上传结果。
5. **单机可跑、集群可扩**：Docker Compose 一键启动；无状态后端可横向扩展（SSE 会话状态放 Redis）。
6. **协议先行**：REST + SSE 事件 + 卡片 schema 先定义，前后端并行开发，OpenAPI 生成 TS 类型。

MCP Server 已落地（2026-10-10）：bootstrap 的 `OfferPilotMcpTools` 通过 resume/job 应用层直接调用 `ResumeDiagnoser` / `JobMatcher` 和 `JobService`；platform 只承载 API Key 过滤器与配置，不依赖业务模块。前两项无 owner / 持久化服务；搜索仅更新公开岗位缓存。Spring AI 1.0.0 SSE 的 `/sse` 与 `/mcp/message` 由密钥过滤器保护，默认关闭。工具及连接契约见 [05 §19](05-接口文档.md#19-mcp-server-工具定义已实现)。

### 2.1 分层职责

| 层 | 职责 | 关键约束 |
| --- | --- | --- |
| 页面 / 组合 / 状态（前端） | 交互、渲染、客户端状态、服务端缓存 | 无业务规则重复实现；所有 AI 结果来自事件流 |
| 接入层 | HTTPS、静态托管、反向代理、SSE 透传 | `proxy_buffering off`、`read_timeout ≥ 300s` |
| Web 层 | 参数校验、认证授权、限流、SSE 生命周期 | 不含业务逻辑；统一响应包裹与错误码 |
| Agent 内核 | 规划、分派、工具循环、反思、事件发布 | 无直接 SQL；通过领域服务与工具访问数据 |
| 领域服务 | 简历、岗位、看板、面试、规划、知识库、记忆、通知的业务规则 | 可被 Controller、工具、调度任务复用 |
| 基础设施 | 模型网关（路由 / 回退 / 观测）、向量库、文件、缓存、事件总线、调度 | 对外部依赖的唯一出口 |

## 3. 后端模块划分

采用 Maven 多模块的模块化单体：业务域各自拥有构建模块，但只有 `offerpilot-bootstrap` 提供 Spring Boot 启动入口，竞赛期不拆业务微服务。

```text
backend/
├── pom.xml                    # 聚合父工程与统一依赖版本
├── offerpilot-bootstrap/      # 唯一启动类、运行配置、Flyway、Prompt
├── offerpilot-platform/       # common、config、llm、mcp 等技术适配器
├── offerpilot-agent/          # agent、conversation：编排、事件、会话、审批
├── offerpilot-identity/       # auth、user：认证与用户
├── offerpilot-resume/         # resume：简历与文件
├── offerpilot-job/            # job、board：岗位与求职看板
├── offerpilot-career/         # discovery、career、knowledge：职业探索、规划与知识库
└── offerpilot-interview/      # interview：模拟面试
```

跨模块只通过 application 层定义的 interface 与契约协作；不得直接依赖其他模块的 Controller、Repository 或持久化实体。`offerpilot-platform` 只承载技术横切能力，不承载业务规则。

### 3.1 Agent 内核核心类型

```java
// 计划（结构化输出）
public record Plan(String goal, List<PlanStep> steps) {}
public record PlanStep(String id, String title, ExpertType agent,
                       Map<String, Object> inputs, List<String> dependsOn) {}

public enum ExpertType { CAREER_DISCOVERY, RESUME, JOB, INTERVIEWER, COACH }

// 事件（可辨识联合，前端一一对应）
public sealed interface AgentEvent permits RunStarted, PlanCreated, StepUpdated,
        ReasoningDelta, TextDelta, ToolCall, ToolResult, UiCard, ApprovalRequired,
        Citation, Usage, ErrorEvent, RunCompleted {}

// 工具策略
public enum ToolAccess { READ, WRITE, EXTERNAL_SIDE_EFFECT }
public record ToolPolicy(String toolName, ToolAccess access, boolean requiresApproval,
                         Duration timeout, int maxCallsPerRun) {}
```

### 3.2 专家 Agent 的组装方式

每个专家 Agent 是一个 `ChatClient`，通过工厂按需装配：

```java
ChatClient client = ChatClient.builder(modelGateway.chatModel(ModelTier.FLASH))
    .defaultSystem(promptRepository.load("career_discovery/system.st", version))
    .defaultAdvisors(
        guardrailAdvisor,                      // 输入注入检测、文档隔离
        piiMaskingAdvisor,                     // 可选脱敏（按用户偏好）
        MessageChatMemoryAdvisor.builder(jdbcChatMemory).build(),
        retrievalAdvisor.forCollection("occupations"),   // 仅需要 RAG 的 Agent 装配
        usageLoggingAdvisor)                   // token / 耗时落库并发 usage 事件
    .defaultTools(discoveryTools, memoryTools)  // @Tool 本地工具
    .defaultToolCallbacks(mcpToolProvider.callbacksFor(userId))  // MCP 工具（按用户启停）
    .build();
```

工具循环由 Spring AI Advisor 承担；`ApprovalService` 在工具执行前检查 `ToolPolicy`，需要审批时发布 `ApprovalRequired` 事件并挂起当前步骤（`CompletableFuture` + Redis 超时），用户决策通过 REST 回传后继续。

## 5. 技术选型与理由

### 5.1 后端

| 领域 | 选型 | 备选 | 选择理由 |
| --- | --- | --- | --- |
| 语言 / 运行时 | Java 17 LTS | Java 21 LTS | 团队环境统一、长期支持且满足 Spring Boot 3.3 的最低要求；升级到 21 前持续避免使用 21 专属 API |
| 应用框架 | Spring Boot 3.3.5 + Spring MVC | WebFlux | MVC 心智简单；SSE 使用 `SseEmitter`，Spring AI 的流式 `Flux` 在边界通过 Reactor 有界弹性调度器桥接 |
| AI 框架 | Spring AI 1.0.x | LangChain4j 1.19 | 保留 DeepSeek、OpenAI、pgvector 与 MCP starter，并与 Java 17 基线兼容；工具循环仍可通过 Advisor 扩展 |
| 向量库 | PostgreSQL + pgvector | Milvus / Qdrant | 业务库与向量库合一，减少一个运维组件；HNSW 满足十万级向量；全文检索 `tsvector` 可做混合召回 |
| 缓存 / 队列 | Redis 7 | RabbitMQ | 限流、SSE 事件缓冲、审批等待、轻量任务队列一站解决 |
| 文件存储 | MinIO | 本地磁盘 / OSS | S3 兼容，本地与云一致；签名 URL 直传 |
| 持久层 | Spring Data JPA + Flyway | MyBatis-Plus | 与 Boot 3.3 / Hibernate 6 集成顺畅；JSONB 与向量列通过自定义类型映射；迁移脚本受控 |
| 认证 | Spring Security 6 + JWT | Session | 前后端分离、无状态、便于横向扩展 |
| 弹性 | Resilience4j + Bucket4j | 自研 | 模型调用重试 / 熔断 / 超时；用户级限流 |
| 文件解析 | Apache Tika + PDFBox | 纯视觉 | 文本层优先成本低；扫描件走视觉 |
| API 文档 | SpringDoc OpenAPI | 手写 | 自动生成，前端 `openapi-typescript` 生成类型 |

| 领域 | 选型 | 备选 | 选择理由 |
| --- | --- | --- | --- |
| 框架 | Vue 3.5 + TypeScript | React + Next.js | 团队熟悉；Java 承担全部 API，无需 SSR；Vite 开发体验好 |

## 8. 非功能设计

### 8.1 性能

- 模型：默认 Flash 档；规划与意图识别用短 Prompt 与低 `max_tokens`；结构化输出使用 JSON Schema 模式减少重试。
- 缓存：岗位搜索结果按归一化查询缓存 30 分钟；JD 与简历向量缓存；知识库检索结果缓存 10 分钟；Redis 存 SSE 事件缓冲 5 分钟。
- 并发：虚拟线程处理 SSE 长连接；模型调用设置 60s 超时；每用户同时运行 ≤ 2 个 Agent Run。
- 前端：路由懒加载；重型依赖（ECharts、shiki 语言包、MediaPipe wasm）按需加载；消息虚拟滚动；构建产物长缓存 + 内容哈希。

### 8.2 可扩展性

- 后端无状态：审批等待、SSE 缓冲、限流计数全部在 Redis；可水平扩展多实例（Caddy 负载均衡；SSE 事件通过 Redis Pub/Sub 广播）。
- 新专家 Agent：实现 `ExpertAgent` 接口 + Prompt 模板 + 工具类，注册到 `ExpertRegistry` 即可被 Orchestrator 分派。
- 新卡片类型：后端新增 `cardType` 与 payload record，前端在卡片注册表添加组件；协议无需变更。
- 新 MCP 服务器：设置页添加连接，工具自动进入注册表并受 `ToolPolicy` 默认策略（外部工具默认 READ，写类名称匹配规则需审批）。

### 8.3 可观测性

- `traceId` 贯穿 HTTP → Agent Run → 模型调用 → 工具调用，写入日志 MDC 与响应头。
- Spring AI Observability 指标（`gen_ai.*`）经 Micrometer 暴露；每次调用的模型、token、耗时、成本估算写 `llm_usage_logs`。
- Actuator：`health`（含 DB、Redis、MinIO、模型可达性）、`metrics`、`prometheus`（可选接 Grafana）。
- 前端：错误边界上报（简易 `POST /client-logs`，P1）。

### 8.4 安全

- 认证当前实现：JWT access 12 小时，密码 BCrypt(12)；访客令牌独立有效 30 天。refresh 7 天（HttpOnly、Secure、SameSite=Lax）仍为后续设计；当前过期要求重新登录，不自动重放请求。
- 授权：所有资源按 `user_id` 隔离；管理员接口 `ROLE_ADMIN`。
- 输入：Bean Validation；文件类型白名单与魔数校验；大小限制 10MB；上传扫描（ClamAV 可选）。
- AI 安全：见 [04-AI技术方案 §10](04-AI技术方案.md)。
- 传输与存储：全站 HTTPS；MinIO 私有桶 + 签名 URL；第三方 Token（GitHub）AES-GCM 加密存储。
- 限流：Bucket4j 每用户 60 req/min，模型调用每用户每日 token 上限可配置。
- 供应链：Dependabot；`gitleaks` pre-commit；CI OWASP Dependency-Check（P1）。

## CD-03 画像与长期记忆边界（2026-10-19）

career 的 CareerProfileService 组合本模块 career_profiles 和 career_assessments.confirmed。CareerProfileMemory 是小型应用端口，由 agent 的 CareerProfileMemoryAdapter 实现，调用既有 UserMemoryService 的读取/前缀 upsert；依赖仍为 agent→career，无 career→agent 反向依赖。GET 控制器调用 load 仅导入空字段，领域内部 get 保持只读。显式保存与测评确认在同一事务同步记忆；记忆容量错误回滚本次画像写入，客户端保留草稿。所有画像/测评写入与导入先持 ACTIVE users 行锁，再持画像或测评锁，与记忆开关、隐私删除和 demo reset 顺序一致，阻止迟到写入。推断的模型调用仍不持事务。无新进程、模型调用、自动事实抽取或额外记忆表。

## CD-06 / CD-08 推荐修订与职业对比（2026-10-19）

`CareerRecommendationController → CareerRecommendationService → JdbcTemplate` 归属 career；通过既有 `CareerRecommendForChat` 生成初始候选，V34 保存 owner 私有不可变修订快照。重排只重评该修订的原始候选，不调用检索、embedding 或模型。agent 通过小型 `CareerRerankForChat` 边界访问修订，`CareerWriteTools → ApprovalService` 批准后保存；既有聊天只读推荐保持不写业务表。前端 career feature 复用 shared/api，Chart.js 只负责雷达；无新模块或反向依赖。

## 非聊天后台生成（2026-10-20）

Bootstrap 的既有 `generation` 模块负责跨域编排：`GenerationTaskService` 持久化统一生命周期并管理有界执行器，`GenerationWork` 仅调用各领域应用服务。领域继续保存报告、建议、版本或会话；不通过控制器互调，不新增进程。HTTP 只负责受理，断开连接不取消执行。简历解析和知识向量索引继续使用各自已有的持久化 worker；知识资料文本提取仍为同步无生成模型的文档解析。Agent Run 与生成任务保持各自语义。


## 岗位发现纵向切片（2026-10-20）

job 的 JobService 复用 JobSearchPipeline：FLASH 摘录解析与规则回退、并行本地库/MCP 召回、去重、限量和部分结果。有界线程池（12 工作线程、24 排队位）与 7700ms 外层预算包住解析、召回和岗位持久化，超时返回已发布快照并取消等待；数据库查询设 1s statement timeout。它是搜索服务的计算预算，不含聊天规划、聊天企业目录校验和 HTTP 传输。聊天与后端 MCP 工具复用结果，保留部分结果/逐条来源。

JobLocalSearch 的关键词召回按标题命中与正文命中排序；可选 Ollama bge-m3 查询向量和同空间、同 payload hash 的持久向量按 RRF 融合，失效/缺失/失败保留关键词。JobEmbeddingIndexer 每分钟最多索引10条公开非示例岗位，不索引私有导入资料。JobRecommendationService 仅在本地真实岗位库中按目标、画像、简历和城市规则评分；JobRecommendationContext 是 job 的只读应用端口，由 bootstrap JobRecommendationBridge 组合 career 的 get 与 resume 的 ResumeJobSignals，无 job→career 仓储或模块依赖。每日缓存与账号/体验重置生命周期同步，空输入或零候选返回空流。匹配继续沿用 V41 JOB_MATCH 与既有证据校验，不新增生成链路。
